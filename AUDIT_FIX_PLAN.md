## ПРОБЛЕМА 1 — userspace-программа не возвращается в shell (HIGH)

Статус: ИСПРАВЛЕНО 2026-10-14 (рабочее дерево, без коммита). Валидация: свежая
scratch-копия /tmp/muzix-verify — `make rom` exit 0 (ROM-валидаторы PASS,
`_CODE` ends 0xB831), `make check` exit 0 (all gates PASS, host tests 9/9),
эмулятор: `date\nuptime\ndate\n` — промпт после КАЖДОЙ программы и вторая
`date` выполняется; `ls\nls` — обе и промпты между; `uptime\ntop` — смоук зелёный.

Корневая причина (единственный дефект, всё остальное — следствия):
`p_messbuf` в `muzix_ipc_proc_t` перегружен — мини-receive в блок-ветке
(`kernel/ipc.c`, бывшая строка 327) перезаписывал его адресом буфера приёма,
хотя единственный читатель поля — очередь отправителей в mini_rec (там же),
которая читает через него сообщение поставленного в очередь отправителя.
Запрос-и-ответ маршрутизированного syscall'а как раз совмещает оба: запрос
стадируется в `g_route_msg[slot]`, при занятом сервере mini_send ставит этот
указатель в очередь, и тот же syscall тут же блокируется на ответ в mini_rec —
блок-ветка затирала указатель адресом стекового локала хендлера. Сервер,
обходя свою callerq, читал мёртвый кадр ядерного стека: трассе
(`RECV: d=02 via=queue snd=01 src=02`, `RECVQ: buf=FF6C` против
`ROUTQ: buf=DE17` = `&g_route_msg[1]`) FS забирал свои же ответные байты
(m_source = сам FS) как запрос от шелла, отвечал сам себе
(`SEND: c=02 d=02`), и штамп `slots[FS].ipc_client` уходил в 2 — после чего
копирование SRV_COPY_FROM_CLIENT для промпта шло не от того клиента и вывод
шелла до консоли не доходил.

Фикс (kernel/ipc.c): убрана запись `caller_ptr->p_messbuf = m_ptr;` из
блок-ветки mini_rec + комментарий с измерением. У паркованного приёмника
читателя у поля нет: доставка пишет `p_msg`, а userspace-буфер достигается
через `p_user_addr`. В MINIX поле общее для очереди и приёма (один буфер на
процесс), здесь путей два с разными буферами — отсюда и алиасинг.

Дефект A (exec readies parked parent) остаётся как документированное поведение:
`PROC READY: slot=01` сразу после `EXEC SYS: load rc=00` (публикация
`woken_slot` из exec_loader.c, контракт «Wake Mutations Are Sticky») будит
шелл из wait-парковки раньше выхода ребёнка; one-shot `SYS_WAIT` возвращает 0,
зомби подбирается wait'ом СЛЕДУЮЩЕЙ команды (шелл вызывает wait один раз,
результат игнорирует — Known Limitations в AGENTS.md). С фиксом IPC это
безвредно: во всех прогонах команды выполняются подряд, промпты на месте.
При желании усилить: `wait()` в цикле до pid > 0 в shell/shell.c:229 —
документированное сходящееся поведение; не делалось как вне плана.

## ПРОБЛЕМА 2 — ввод из консоли идёт рывками (HIGH)

Статус: ИСПРАВЛЕНА (2026-10-14, два фикса в рабочем дереве, не закоммичены).
Симптом: каждый символ arrives не по прибытии, а по истечении 240-тикового
(~2 s) дедлайна парковки `read()`.

Доказано инструментацией scratch (трассы WINPUT/WEXP в `muzix_proc_table_*`,
UISR на входе `_muzix_uart_rx_isr`, host-сторона эмулятора):

1. За пул/фифо прогоном `printf 'date\n'` и медленной FIFO-подачей
   (`mkfifo`; `(sleep 4/5; printf 'date\n' > fifo) &` + `< fifo`):
   `WINPUT` — 0 срабатываний за прогон, `WEXP` — все пробуждения. Шелл всегда
   просыпается по дедлайну, никогда по флагу UART.
2. `UISR:` (трасса на входе ISR, добавлена в tick.s) — 0 срабатываний:
   обработчик прерывания UART не выполняется НИ разу.
3. Host-сторона эмулятора (fprintf в `emulator/z80pack/z80pack.c`): вектор
   тика `0x82` поднимается 1922 раза (IM2 и CTC ch1 работают), вектор UART
   `0x84` — 0 раз. Детектор фронта (`z80pack_ctc_tick`, edge по
   `have_byte && irda && !ctc_uart_int_prev`) срабатывает ОДИН раз за прогон и
   в этот момент `ctc_irq_enabled[2]=0`, `ctc_vector_base=0x00`, т.е. CTC ch2
   ещё не вооружён.

Доинструментирование (2026-10-14, scratch2) закрыло вопрос полностью — с
чётчиком инструкций на переходах уровня/`prev`, на записи IER ($69), на
управляющих словах CTC ch0/ch1/ch2 и на каждом заборе байта (RBR) и каждом
`pump`:

    insn=1..5        stdin pump: 'd','a','t','e','\n'  (FIFO стартует эмулятор
                    только при открытии писателем: `< fifo` блокирует open,
                    поэтому байт «через минуты» физически недостижим — он
                    доступен с инструкции 1; это свойство стенда, не системы)
    insn=135372      out ($69),#0x01     <- IER bit0 (kernel_main.c:151)
    insn=135373      edge 0->1, ctc_irq_enabled[2]=0, vec_base=0x00  ФРОНТ ПОТЕРЯН
    insn=136273      ctc ch0 vec_base=80
    insn=136295      ctc ch2 ctrl=d7 (irq_en=1)   <- ch2 вооружён
    insn=6123375..   RBR drains d,a,t,e,\n  (первое чтение — в конце boot,
                    6M инструкций спустя; задержки нет: шелл забирает байты
                    опросом, park не происходит)
    raise_irq vec=84: 0 раз, UISR: 0, WINPUT: 0, WEXP: 11

Механизм окончательно: уровень INT 16550 (`have_byte && irda`) поднимается в
окне между `uart_init` (IER bit0) и `tick_init` (вооружение ch2, vec_base,
`im 2`); фронт срабатывает при невооружённом ch2, вектора не даёт, а `prev`
залипает в 1, пока буфер не осушится. Подозрение на модель уровня в эмуляторе
опровергнуто: когда байт прибывает на уже вооружённый ch2 (промпт, машина в
HALT), edge даёт `vec=84`, `halted=1`, ISR выполняется, `WINPUT` срабатывает,
чтение — через ~32k инструкций (~0.26 s эмул. времени). Эмуляторная модель
верна; дефект — порядок инициализации ядра (реальный hardware-дефект: CTC
считает фронты, уровень, поднятый до вооружения, фронта уже не даст).

Фиксы (в рабочем дереве, НЕ закоммичены):

1. `platform/zeta-v2/uart_io.s`: `out ($69),#0x01` убрано из
   `_muzix_zeta_uart_init`; новый entry point `_muzix_zeta_uart_rx_irq_enable`
   (объявлен в `uart_io.h`), который `kernel/kernel_main.c` вызывает СРАЗУ
   ПОСЛЕ `muzix_tick_init()`. Байт, пришедший раньше, ждёт в FIFO с уровнем
   LOW (irda=0); включение бита поднимает уровень 0->1 уже при вооружённом
   ch2 — вектор рождается как должно.
2. `kernel/kernel_loop.c`: пробуждение читателей теперь по УРОВНЮ, а не
   только по одноразовому флагу ISR — `kernel_wake_console_readers()` =
   `muzix_uart_rx_pending() || muzix_zeta_uart_available(0)`. Закрывает
   второй измеренный случай: прерывание приходит до парковки читателя (окно
   boot), холостой проход ядра съедает флаг, а байт всё ещё лежит в FIFO —
   раньше читатель ждал полные 240 тиков. Один `in` на возврате из HALT;
   цена — как у флагового пути.

Валидация (свежая копия /tmp/muzix-verify2 + инструментированная
/tmp/muzix-scratch2): `make clean && make rom && make check` — зелено (9/9
host-тесты, all gates PASS; в scratch2 падает только `test_tick` — артефакт
инструментации tick.s). Эмулятор-смоук `printf 'uptime\ntop\n'` — uptime/top
отвечают, banks `20 21 22 23`, exit 0. Критерий Проблемы 1
(`printf 'date\nuptime\ndate\n'`, промпт после каждой команды) — проходит.
После фикса в FIFO-прогоне: `IER` на insn=136304 (после ch2 arm=136295),
edge при `irq_en2=1 vec_base=80`, `raise_irq vec=84`, `UISR:1`; в сценарии
«байт на промпт с детектом строки `/> `» — edge, `halted=1`, ISR, `WINPUT=4`,
чтение через ~0.26 s эмул. времени вместо ~2 s дедлайна. На чистом эмуляторе
тот же сценарий печатает `/> uptime` + `up 0 days, 0:00:08` сразу у промпта.

Примечание для критерия «WINPUT на каждый байт»: один ISR на пачку байтов в
FIFO — это и есть поведение 16550 (INT — уровень); уровень-фикс гарантирует,
что ПОКА байт лежит в FIFO, любой паркующийся читатель будет разбужен —
«на каждый байт» в смысле «ни один байт не уходит в дедлайн».

Инструментация (в /tmp/muzix-scratch, НЕ в дереве; host-тест test_tick падает
там же по причине инструментации tick.s — для прогонов эмулятора это ок):
- `kernel/proc_table.c`: трейсы `WINPUT: slot=`/`WEXP: slot=` в двух wake и
  `PARK: slot= t=` в park; `kernel/kernel_loop.c`: сброс ring на простое;
  `platform/zeta-v2/trace.h`: ring 4096; `platform/zeta-v2/tick.s`: `UISR:`
  на входе ISR (+ `.globl _muzix_trace_write`).
- `emulator/z80pack/z80pack.c`: fprintf на uart-edge и в raise_irq
  (stderr). FIFO-прогон: `mkfifo /tmp/fifo_in; (sleep 5; printf 'date\n' >
  /tmp/fifo_in) &` затем `./z80pack-emu -s muzix ../build/muzix-zeta-v2.rom
  -i -c 120000000 < /tmp/fifo_in`.

## ПРОБЛЕМА 3 — оптимизация загрузки (perf)

Статус: ИСПРАВЛЕНА (2026-10-14, правка в рабочем дереве, НЕ закоммичена).
Было: принятое отклонение ~6s против ~4s у HEAD (причина per AGENTS: staged
256B-копирование через MM-примитивы). Проверка по плану: `make check` +
`make rom` + эмулятор (`up 0 days, 0:00:0X` против ~6s).

Диагностика (scratch /tmp/muzix-perf, TX-штампы инструкций на трейс-строках):
- Весь boot до баннера шелла = 3.41M инструкций; фаза exec (160 чанков) =
  88% от неё. Прод-прогон без `-t` — трейсов нет, зеркало не считается.
- Внутри чанка (`-t` для атрибуции): `BOOT COPY` на 256B = ~8.5K инструкций;
  фаза чтения (два ROM-блока по 512B + книга) = ~23.5K. LDIR-копия 512B сама
  по себе ≈2.6-2.9K — то есть 3/4 стоимости `BOOT COPY` был C-байтовый цикл
  стейджинга (`g_copy_staging[i]=src[i]`, ~30 инструкций на байт), а не
  переключение карт.
- Подозрение на «temp-map per chunk» не подтвердилось: save/load_map —
  единицы порт-записей; жир — стейджинг. Модель уровня/edge (Проблема 2) тут
  ни при чём.

Фикс (platform/zeta-v2/context_switch.c): `zeta_copy_kernel_to_user` теперь
делает прямой LDIR из буфера вызывающего, когда диапазон источника НЕ
пересекает window 1 — единственное окно, которое заменяет temp-map
(region-2 ремапится в window 1, region-1 и есть window 1, region 0/3
отвергаются). Окна 0/2/3 сохраняют страницы `muzix_live_banks`, поэтому
источник читается одинаково до и после переключения. window-1 источник
(или диапазон, straddling границу из window 0) по-прежнему стейджится.
Старый код:
```c
    for (i = 0; i < len; i++) {
        g_copy_staging[i] = src[i];
    }
    ...
    } ctx = { state, write_addr, len };
```
Новый: источник проверяется и выбирается (`ldir_src`), а `ctx` несёт его;
`copy_kernel_to_user_callback` пишет `muzix_zeta_staged_src` из `ctx->src`
вместо жёсткого `&g_copy_staging[0]`. Гейт check_memory_manager.rb не
задет — вызывающих примитива не прибавилось, правка внутри самого примитива.

Замеры (один харнесс на трёх сборках: 25bd81c / фиксы П1+П2 / +этот фикс):
- `printf 'uptime\ntop\n' | emu -i -c 150M` → `up 0 days, 0:00:06` /
  `0:00:06` / **`0:00:04`** (цель плана — вернуть ~4s).
- Баннер шелла: 3,412,624 / 3,412,624 / **2,422,636** инструкций.
- Idle halt fraction (`</dev/null`, 120M циклов): 54.29% / 54.13% /
  **64.31%** — вернулись к до-аудитным ~63%.
- Приём-критерий Проблемы 1 (`date\nuptime\ndate\n`) — проходит, Проблема 2
  (ввод на промпте → ISR → WINPUT → чтение за ~0.26s) — без регресса.

Валидация: свежая копия /tmp/muzix-verify3 — `make clean && make rom` (512
KiB), `make check` (9/9 host, all gates PASS), смоук `uptime/top` (banks
`20 21 22 23`, exit 0, без MNT FAIL), приём `date/uptime/date`.

## ПРОБЛЕМА 4 — `ls` не выводит листинг диска (регрессия микроядерного перехода)

Статус: ИСПРАВЛЕНА (2026-10-14, правки в рабочем дереве, НЕ закоммичены).
Симптом: `/> ls` — пустая строка и следующий промпт (худший случай: `ls`
зависал в бесконечном цикле readdir, выводя пустые имена).

Диагностика (scratch /tmp/muzix-ls + /tmp/muzix-dbg, трассы send/recv,
`p_flags` дестинации, стек вызовов): два независимых дефекта, оба из перехода
на микроядерную архитектуру:

1. **Дети fork не registrierованы в IPC-таблице.** `muzix_ipc_register_server()`
   вызывалась только из kernel_main для четырёх слотов, которые он сам
   поднимает (0, FS, MM, PM, шелл). Слот ребёнка (5) оставался с
   `P_SLOT_FREE`: `MSEND bad: caller=12 dest=15 dflags=05` — 53 отказа за
   прогон. mini_send проверяет флаг ТОЛЬКО у назначения, поэтому запросы
   ребёнка уходили, а каждый ответ FS возвращался с `E_BAD_DEST`: `ls`
   парковался в syscall и получал парковочный плейсхолдер 0 вместо ответа —
   readdir возвращал 0 вечно. `date` выживал только потому, что вывод
   происходит в FS ДО отправки ответа.
2. **Обработчики файловых операций FS-сервера — заглушки.** `servers/fs/
   fs_server.lk` линкует fs_server + fs_clock + tty_device + bank-примитивы
   и ничего больше; `handle_open`/`handle_readdir`/`handle_read`/`handle_stat`
   отвечают -1. Приложением это не видно было из-а дефекта 1: открытие
   возвращало 0 (плейсхолдер) — «успех» с неверным fd.

Побочно найден третий дефект того же рода: в userspace-пути перехвата
`if (syscall_num == MUZIX_SYS_YIELD) return 0;` — а `MUZIX_SYS_YIELD == 10 ==
пользовательский SYS_OPEN`. Ловушка не различает пространства номеров, поэтому
КАЖДЫЙ `open()` отвечал 0 (валидный с виду fd) и `ls` читал каталог через fd 0.

Фиксы (в рабочем дереве, НЕ закоммичены):

1. `kernel/syscalls_ipc.c`, `muzix_handle_fork()`: ребёнок регистрируется в
   IPC-таблице (`unregister` + `register` — идемпотентно при переиспользовании
   слота); `muzix_handle_exit()` снимает регистрацию. Серверы не затронуты
   (kernel_fork_server идёт через system-service dispatch, kernel_main
   регистрирует свои четыре слота сам).
2. `kernel/rom_read.c` + `rom_read.h`: ROM-FS перехватчики `muzix_rom_open_path`
   / `muzix_rom_readdir` / `muzix_rom_fd_is_synthetic` — разрешение пути и обход
   корневого каталога через тот же блок-устройство и раскладку MINIX-v1,
   которыми пользуется exec-путь. Дескриптор синтетический (inode + 4, диапазон
   5..35 — не конфликтует с консольными 0/1/2).
3. `kernel/syscalls_ipc.c`: `SYS_OPEN`/`SYS_READDIR`/`SYS_CLOSE` перехватываются
   ядром ДО таблицы маршрутизации (как TIMES/PROCTAB/RTC); коллизия с
   `MUZIX_SYS_YIELD=10` устранена удаление раннего перехвата из userspace-пути
   (внутренние номера принадлежат record-driven диспетчеру); аргумент-указатель
   берётся как `(uint16_t)` аргумента — ловушка знаково-расширяет 16-битное слово
   (0x888A приходит как 0xFFFF888A), и прежняя проверка `arg < 0` отвергала
   любой адрес в window 2.

Валидация (свежая копия /tmp/muzix-ls): `make check` — 9/9 host, all gates
PASS; смоук `uptime/top` — `up 0 days, 0:00:04` (фикс Проблемы 3 цел), без
MNT FAIL; приём `date/uptime/date` — 2 вывода date; `/> ls` (и при вводе на
простой) выдаёт полный листинг: `.`, `..`, readme, hw-notes, copy-notes,
echo, cat, ls, date, top, uptime, loadavg, hwdiag, shell, fs_server,

Известные остатки (не в scope этой правки): обработчики read/stat/seek FS так
и остаются заглушками — `cat file` не работает; шелл печатает промпт посреди
вывода команды из-за одноразового `SYS_WAIT` (задокументированное поведение,
проверяемое не здесь).

## Раунд 2 пользовательских регрессий (2026-10-15)

Пользователь на сборке c17d29f: (1) ввод комманд снова рывками, (2) `ls`
после листинга не возвращается в шелл, (3) `cat` не печатает readme
(и `hwdiag`: `[FAIL] ROMFS read`). Диагностика — scratch /tmp/muzix-sess c
watchpoint на адрес штампа парковки слотов и трассами заряда/контекста.

Причины и фиксы (все три — в рабочем дереве, НЕ закоммичены):

1. **Рывки ввода: проверка консоли жила только на halt-return.** Host-side
   хронометраж: байт записан в 614.640, а `stdin pump` (единственное место,
   где гость забирает байт из трубы — и только через чтение LSR!) выполнился
   в 618.04 — 3.4 c спустя. `kernel_wake_console_readers()` вызывалась лишь
   после `kernel_halt()`, а в этом окне машина НЕ засыпала: дедлайн парковки
   шелла не истёк, а FS крутился в собственном цикле пробуждений. Фикс:
   та же проверка в `case MUZIX_KERNEL_LOOP_RUNNING` (kernel/kernel_loop.c) —
   один IN на проход цикла; замер: байт подхвачен за 7.6 ms.
2. **Цикл пробуждений parked-слотов: у `tick_stamp` два хозяина.** Это поле
   было и дедлайном парковки (`park()` пишет, `wake_expired()` тестирует) и
   отметкой заряда (`charge()` читает и перезаписывает `now`, плюс re-stamp на
   dispatch в proc_context.c). Watchpoint поймал запись tick-счётчика в
   `0xFFFF`-дедлайн припаркованного слота из `muzix_tick_add_process_time`
   (PC=0230/0253 в tick.s; caller опросом стека не опознать — SP указывает в
   `g_saved_user_context`, switch-scratch). Дедлайн мгновенно «истекал» →
   слот переставлялся в ready → dispatch → парковка → по кругу: машина не
   засыпала, отсюда и рывки. Фикс структурный: новое поле
   `muzix_proc_slot_t::charge_stamp` — все учетные записи (charge, два
   пробуждения, init, fork, dispatch re-stamp) переведены на него;
   `tick_stamp` остался только дедлайном. Замер idle halt (без ввода, 120M
   циклов): 54.1% → 64.9-66.8% (до-аудитное ~63%).
3. **`cat`/hwdiag: у FS-сервера нет чтения файлов (заглушка).** Добавлены
   `muzix_rom_seek` / `muzix_rom_read` в kernel/rom_read.c (тот же блок-девайс
   и тот же обход зон, что у exec-пути; файловое смещение — плоская таблица
   по синтетическому fd) и перехват `SYS_READ`/`SYS_SEEK` в ядре, как
   OPEN/READDIR/CLOSE. `cat readme` печатает файл; hwdiag ROMFS read — OK.
4. **Промпт после команды: `getcwd` вешал шелл.** Промпт обновляется через
   `refresh_cwd()` → SYS_GETCWD → маршрут в FS, чей `handle_getcwd` — заглушка;
   ответ до шелла не доходил, и он висел в IPC-парковке до следующего
   нажатия — снаружи это «ls не вернулся в шелл». Фикс: ядро отвечает на
   GETCWD само (у ROM-FS один каталог, «/»), как на TIMES/PROCTAB/RTC.

Валидация (свежая копия /tmp/muzix-f4): `make clean && make rom`, `make check`
(9/9 host, all gates PASS), смоук `uptime/top` (`up 0 days, 0:00:04`, banks
`20 21 22 23`, без MNT FAIL), приём `date/uptime/date` (2 вывода date),

## Раунд 3: применены две оптимизации из обзора недокументированных Z80 (2026-10-15)

По запросу пользователя внедрены пункты таблицы приоритетов из
`docs/z80-undocumented-instructions.md`. Обе — в рабочем дереве, staged.

1. **`EXX` + `EX AF,AF'` в тик- и uart-обработчиках** (`platform/zeta-v2/tick.s`).
   Было: 6 push + 6 pop = 132T стекового трафика на прерывание. Стало: два
   обмена (8T) на AF/BC/DE/HL + push/pop только IX/IY (они не покрыты `exx`,
   и прерванный C-код держит в них frame pointer). Замер (эмулятор, idle без
   ввода, 120M циклов, детерминированно): halted 64.25% → **65.01%**,
   инструкций +128K (рост кода — честная плата). Инвариант ABI записан в
   AGENTS.md: альтернативный набор принадлежит обработчикам и никому больше
   (`EXX` в дереве не используется больше нигде — проверено грепом).
2. **Битмап-обход аллокатора страниц на ассемблере**
   (`platform/zeta-v2/bitmap_ops.s`, + заголовок и host-стабы
   `test_host/bitmap_host.c`). Было: `zeta_memory_alloc_page()` сканировал
   `uint32_t` маску выражением `(g_used_pages & ((uint32_t)1u << index))` —
   SDCC на каждом шаге строит свежий переменный сдвиг 32-битной единицы
   (~3.5k T на 32 бита). Стало: `muzix_bitmap_alloc(map, byte_count)` —
   обход байтов (`CPL` + тест), затем `SRL` по битам с построением маски
   `SLA` в такт (~470T на полный скан), установка бита обычным `OR`;
   `muzix_bitmap_release` — снятие через `~mask & (HL)`. Хранилище —
   `uint8_t g_used_pages[4]` (тем же 4 байтами). Модуль добавлен в
   KERNEL_S_MODULES, KERNEL_LINK_ORDER, FS_SERVER_PLATFORM_RELS и
   servers/fs/fs_server.lk.

Что сознательно НЕ применено (обосновае в AGENTS.md и в обзоре): SLL — в
дереве нет паттерна `(x<<1)|1`; IXH/IXL — +4T/+1 байт против H/L, выигрыш
только при дефиците регистров; `BIT/RES/SET b,(IX+d)` — индекс бита в
битмапе известен только в рантайме, поэтому индексированная форма стоит
8-стороннего dispatch'а, что хуже имеющегося обхода; `DD CB rot→reg` и
переменный сдвиг `(src[i] >> j)` в `rtc_ds1302.c` — реальный, но
низкочастотный выигрыш против бит-точного протокола с тремя задокументированными
ловушками; оставлено до появления железа. sdasz80 не принимает мнемоники
DD/FD вовсе — любое будущее применение только `.db` с комментарием-декодировкой.

Валидация (текущее дерево): `make rom` COMPLETE, `make check` — 9/9 host,
all gates PASS; смоук: `ls` (17 записей), `cat readme`, `hwdiag` — все
проверки passed, uptime `0:00:04` (фикс Проблемы 3 цел), banks `20 21 22 23`,
exit 0; замер idle: halted 65.01%.
